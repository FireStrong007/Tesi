# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

VitaBridge: a serverless PWA (React 19 + TypeScript + Vite + Tailwind v4 + shadcn/ui) that replaces Gadgetbridge for Garmin bands (target: vívosmart 5). It talks to the band over **Web Bluetooth** and stores everything in **SQLite WASM on OPFS** inside a worker. No backend. The protocol code is a port of Gadgetbridge (AGPL-3.0); it has been verified only against the built-in simulator, never against a real band.

Language conventions: UI strings, README and log messages for the user are in **Italian**; code comments and identifiers are in English.

## Workspaces

npm workspaces (`package.json` at the root, one `node_modules`):

- **`packages/core`** (`@bridge/core`): code with no browser, Bluetooth or server dependency — `metrics`, `format`, `time-zone`, `colors`, `day-data`, `range-data`, `db/sql`, `db/queries` (the data queries; `apps/web/src/lib/db/repo.ts` re-exports them), `comparison/` (aggregate, cohort, daily-values, types), `server/` (schema, views, server-source). Consumed as TypeScript source (`"exports": { "./*": "./src/*.ts" }`, no build step), imported as `@bridge/core/<path>`. Its tsconfig has no DOM and no Node types, so the compiler rejects browser or Node APIs there. Core must never import from `apps/*`.
- **`apps/web`** (`@bridge/web`): the React app (Vite, `index.html`, `public/`, `src/`, `tests/`), still including the Bluetooth, demo and import code until Fase 3. Login, password change and the administrator's area are in `src/auth.tsx`, `src/lib/api.ts`, `src/pages/{login,change-password,admin}.tsx`: `App.tsx` shows login first, then the area of the account's role. Path alias `@/` → `apps/web/src/`.
- **`packages/server`** (`@bridge/server`, Node ≥ 24): Hono API, one process per app (`APP=vitabridge|heartbridge`), configuration only from environment variables (`src/config.ts`, `.env.example`; in development `.env` at the root). See "Server" below.
- **`packages/synth`** (`@bridge/synth`, development and tests only): FIT decoder/encoder and profile, the demo generator, `server/fit-to-server.ts`, and the synthetic research databases (`garmin-db.ts` reuses demo generator + fit-to-server, `gima-db.ts` generates rows directly; some sections deliberately empty, real invalid values included). The web app imports the FIT code from here until Fase 3.

Below, paths without a workspace prefix are in `apps/web/` unless listed above as core.

## Commands

```bash
npm install
npm run dev                      # API server (:8787, tsx watch) + Vite (:5173, proxies /api); extra args go to Vite: npm run dev -- --port 5174
npm run dev:web / dev:server     # one of the two
npm run gen:synthetic            # data/synthetic-garmin.db + data/synthetic-gima.db (made-up participants, real schemas)
npm run admin:create -- <nome>   # new administrator (temporary password printed once, change forced, audit_log); never from the web
npm run admin:reset-password -- <nome>   # new temporary password for any account (administrator recovery); after the build: node packages/server/dist/admin.js
npm run build                    # apps/web (tsc -b && vite build -> apps/web/dist/) + packages/server (esbuild -> dist/server.js, dist/admin.js)
npm run preview                  # serves apps/web/dist
npm run typecheck                # tsc -b (packages/core + apps/web)
npm test                         # vitest run, projects core, synth, server, web (tests/**/*.test.ts in each, node, TZ=Europe/Rome)
npx vitest run --project core               # one workspace
npx vitest run apps/web/tests/sync.test.ts  # single test file
npx vitest run -t "pairs, syncs"            # single test by name
GB_EXPORT=/path/gadgetbridge_*.zip npx vitest run apps/web/tests/server-format.test.ts   # checks against a real Gadgetbridge export (skipped without it; never commit an export)
npm run gen:fit-profile          # regenerate packages/synth/src/fit/profile.ts (needs ../Gadgetbridge checkout + python3)
```

There is no linter configured. CI (`.github/workflows/pages.yml`) runs `npm test` then `npm run build` on every push to `main` and deploys `apps/web/dist/` to GitHub Pages, so both must pass. `apps/web/vite.config.ts` uses `base: "./"` so the build works under any sub-path; keep asset paths relative.

`packages/synth/src/fit/profile.ts` is generated — edit `scripts/gen-fit-profile.py` (the `WANTED` message set) instead.

## Architecture

Data flow: **BLE transport → Multi-Link → GFDI session → FIT files → `fit_file` table → importer → sample tables → repo queries → pages/charts.**

- **`src/lib/garmin/`** — protocol stack. `transport.ts` defines the `BleTransport` interface (real impl: `WebBluetoothTransport`). `multilink.ts` registers services on handle 0 and handles the GFDI channel plus realtime channels (HR, steps, floors, Body Battery, respiration, SpO₂). Packets are COBS-framed with Garmin CRC (`cobs.ts`, `crc.ts`). `gfdi.ts` builds/parses GFDI messages; `session.ts` (`GarminSession`) does the handshake and file sync (directory → download → archive on band).
- **`src/lib/demo/`** — `FakeWatch` implements `BleTransport` and speaks the real Multi-Link/GFDI protocol; `packages/synth/src/demo/generator.ts` produces realistic FIT files (via `fit/encoder.ts`). The demo mode and the test suite both run the *same* session/decode/import code as a real band, so protocol changes must keep `FakeWatch` in sync.
- **`packages/synth/src/fit/`** — FIT decoder/encoder driven by the generated profile.
- **`src/lib/db/`** — `sql.ts` (core: `packages/core/src/db/sql.ts`) defines `SqlExecutor` (`all`/`run`/`batch`), the only DB interface used by `repo.ts` and `importer.ts`. In the browser it is `DbClient` (`client.ts`), a promise RPC to `db.worker.ts` (OPFS file `/vitabridge.sqlite3`); in tests it is `oo1Executor` over an in-memory DB (`tests/helpers.ts` → `memoryDb()`). Schema lives in `schema.ts` as an append-only `MIGRATIONS` array applied via `PRAGMA user_version` (`migrate.ts`): to change the schema, append a migration and bump `SCHEMA_VERSION`, never edit old entries.
- **Demo profile** — the demo band lives only in a separate user with `user.is_demo = 1` (`ensureDemoUser`, `openDemo`/`leaveDemo` in `app-context.tsx`, active profile in `meta.active_user`); `addDevice` refuses to mix demo and real bands in one profile and Gadgetbridge imports refuse the demo profile, because every query filters by user only. The demo profile never contributes to comparisons or uploads (`repo.shareableUsers`).
- **Schema check** — at startup (and after restoring a database) `checkSchema` in `migrate.ts` compares the DB with a fresh in-memory copy built from `MIGRATIONS`, recreates missing tables/indexes/columns, logs it, and `reprocessSchemaFailures` re-imports files that failed for a missing table or column.
- **Schema conventions** — every sample table has `user_id` and `device_id` (designed for a future multi-patient "doctor area"); all timestamps are **unix seconds**. Raw FIT bytes are kept in `fit_file` (SHA-256 dedup) so data can be reprocessed; if older files arrive after newer ones, the device's samples are rebuilt from all its files.
- **`src/lib/device-manager.ts`** — glue between sessions (real or demo) and the DB: connect, sync, import, battery, live state. `live-recorder.ts` saves live values to `live_sample` each minute; queries append these to synced data but ignore them where FIT files already cover the period.
- **`packages/core/src/`: `metrics.ts`, `db/queries.ts`, `day-data.ts`, `range-data.ts`** — computations deliberately aligned with Gadgetbridge's (sleep stage = end boundary of the period, Garmin stress bands, active + resting calories with BMR prorated). Preserve that alignment when changing them.
- **Activities** — `importer.ts` stores each FIT session in `workout` (all session fields as JSON in `summary`, plus `_zones` from `time_in_zone`), track points in `workout_record`, laps in `workout_lap`. `src/lib/workout.ts` derives zones, km splits, steps/min (Garmin running cadence is strides/min → ×2) for `pages/workouts.tsx`.
- **Comparison with other users** — `packages/core/src/comparison/`: `ComparisonSource` interface (`types.ts`), the only entry point for the UI is `getComparisonSource()` in `apps/web/src/lib/comparison/index.ts` (today `DemoComparisonSource`, a synthetic cohort simulated with `demo/generator.ts` personas; later an HTTP client). It returns, per day (or per Monday–Sunday week for `WEEKLY_METRICS`, i.e. intensity minutes), the other users' median and 25th/75th percentile plus `n`, drawn as a band with the median line; the summary judgement is between people (`periodStanding`: each person's period value from `daily-values.periodValue`, the user's percentile rank among them; `aggregate.summarySentence`), only with ≥ `MIN_VALID_DAYS` (7) valid days. A "valid day" (band worn ≥ 10 h with heart rate) is defined once in `metrics.ts` (`isValidDay`) and applies to day totals of both the user and the cohort. Daily values are defined once in `daily-values.ts` for both the user (`loadRange`) and the cohort; `tests/comparison.test.ts` imports cohort members' FIT files and checks the two paths agree, so keep them in sync when changing importer/loadRange rules. Median, percentiles and ranks need ≥ `MIN_USERS` (5). The week period is the Monday–Sunday week and the month the calendar month (`periodRange`; days still to come are `future` empty slots); `DateNav` has only the two arrows of the period (day, week or month), and only the day opens a calendar. Week/month bar charts always use `sideLabels`, `tightY` and day labels with the month; today (this week for weekly intensity) is a `partial` bar, lighter and dashed, left out of the overlay until it is over (not for HRV, whose last night is already complete); «Confronta» adds the overlay (median line without dots, 25–75 band) and the `info` panel under the chart instead of the tooltip, but never changes what the bars measure (only sleep drops the stacked awake time), and the line must measure what the bar height shows. The demo generator's default persona must keep producing identical files.
- **Research server** — `packages/core/src/server/`: the professor's server schema (`schema.ts`, Gadgetbridge's own Garmin tables: activity samples and battery in seconds, every other table in milliseconds, -1 = not measured, activity STEPS/DISTANCE_CM/ACTIVE_CALORIES are cumulative day counters summed over activity types). `packages/synth/src/server/fit-to-server.ts` replicates Gadgetbridge's FitImporter (FIT → server rows, verified row by row on a real export); `views.ts` shows the server tables as the app's tables (per-minute deltas with LAG per user/device/local day, value at t covers the minute before; the day comes from an explicit `timeZone` option, by default the study's `STUDY_TIME_ZONE` = Europe/Rome for every participant (`packages/core/src/time-zone.ts`), via the TEMP table `tz_offset`, never from SQLite 'localtime'; `ServerComparisonSource.open` refuses a Node process not running in that zone, since loadRange groups days with the process's local time; tests run with TZ=Europe/Rome via vite.config.ts), so `loadRange` and the comparison rules run unchanged on the server; `server-source.ts` is a `ComparisonSource` over the participants of one or more server databases (materialized snapshot). Bands are identified by the Garmin serial number, not the MAC (Web Bluetooth hides it and the vívosmart 5 changes it at every pairing). Known limit of the Gadgetbridge format, kept on purpose for consistency with data uploaded by Gadgetbridge for Android: the midnight totals can be overwritten by the next file. In the comparison the user's own values also go through this format (`apps/web/src/lib/server/user-mirror.ts`: their FIT files converted into the worker's scratch database, `DbClient.scratch()`), so "Tu" and the others share the same rules; the chart bars keep the app's values.
- **Day counters** — the importer restarts the per-activity-type counters at the band's midnight (`bandDay`, offset from `monitoring_info.local_timestamp`, browser offset only as fallback). Migration 7 sets `meta.reprocess_pending`: at the next start every device is rebuilt once from its FIT files (`runPendingReprocess`) and the user sees «Dati ricalcolati».
- **`src/lib/zip.ts`, `gb-import.ts`** — streaming import of Gadgetbridge export zips / loose `.fit` files, matched to devices by serial number in the FIT file.
- **UI** — `App.tsx` + `app-context.tsx`; routing is a custom hash router (`lib/router.ts`, needed for static hosting/PWA). Pages in `src/pages/`, hand-written SVG charts in `src/components/charts/`, shadcn components (new-york style) in `src/components/ui/`. Path alias `@/` → `src/`. `public/sw.js` is a network-first offline cache.

## Server

- **Research data, read-only:** `src/data-source.ts` (`DataSource`): mode `file` (a local copy, development) or `backup` (periodic downloads of the existing server's `GET /admin/backup` with HTTP Basic, checked with `quick_check`, `user_version = 1` and core's schema, then an atomic rename; the last valid copy stays if a download fails; one download at a time, `refresh({ ifOlderThanMs })` for «Sincronizza»). Copies are always opened with `file:…?mode=ro&immutable=1` + `readOnly` + `PRAGMA query_only` (`src/sqlite.ts`): no -wal/-shm files are created next to them. Never open `data/*.db` any other way.
- **Datasets:** `packages/core/src/datasets.ts` is the single list of each app's schema (`server/schema.ts` Garmin, `gima/schema.ts` Gima, both copied from the real servers' `sqlite_master`), the tables a copy must have, the health tables a participant may download and the device columns that may be shown (never `identifier`/`hardware_id`).
- **Isolation:** `src/participant-data.ts` is the only module reading health tables; the participant id always comes from the session, table and column names from the dataset and the copy's schema. Participants never get `participant`, `collection_request`, `upload_batch`, keys or tokens; administrators never get health data. `tests/isolation.test.ts` proves it on both apps.
- **Auth database** (`AUTH_DB`, separate from the data, written only by us; append-only `MIGRATIONS` in `src/auth/store.ts`): `account`, `session` (SHA-256 of the cookie token, CSRF token, inactivity expiry per role: participants 30 days, administrators 8 hours, configurable), `audit_log` (administrators' account actions). Passwords with scrypt; temporary passwords are returned only once. Administrator accounts are created and recovered only with `src/admin-cli.ts` on the server (audit author `cli:<system user>`); the first one also from `ADMIN_USERNAME`/`ADMIN_PASSWORD`.
- **Request rules** (`src/app.ts`): non-GET requests need `Origin` = `PUBLIC_ORIGIN` and, once logged in, `X-CSRF-Token`; login limited per username and per IP (`TRUST_PROXY` → last `X-Forwarded-For` entry); error answers are short Italian messages. The only logger is `src/log.ts`, which hides secret-named fields and the configured secrets; `tests/secrets.test.ts` checks that no password, token, cookie or backup credential reaches the log or an error answer.

## Tests

`packages/core/tests/` holds the tests that need only core (`metrics.test.ts`); `apps/web/tests/` the rest, since they import FIT files through the app's importer. Both use vitest in node, the web ones with the real `@sqlite.org/sqlite-wasm` in memory. `sync.test.ts`/`live.test.ts` run a full `GarminSession` against `FakeWatch` end to end; `protocol.test.ts`, `fit.test.ts`, `sleep.test.ts`, `gb-import.test.ts`, `workout.test.ts`, `transport.test.ts`, `comparison.test.ts` cover the individual layers; `separation.test.ts` covers the demo/real separation, file dedup and the schema check; `server.test.ts` the server views and comparison (synthetic data), `server-synthetic.test.ts` hand-written FIT files with the expected Gadgetbridge rows (band on Tokyo time), `server-format.test.ts` the conversion against a real export (`GB_EXPORT`).
