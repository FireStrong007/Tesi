# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

VitaBridge (Garmin bands) and, from Fase 5, HeartBridge (Gima watches): one project, two configurations. Web apps (React 19 + TypeScript + Vite + Tailwind v4 + shadcn/ui) that show the participants of a study their own data, read **only** from the study's research servers: the data reach those servers from the participants' phones, never through these apps. Each app has its own Node server (`packages/server`) that reads the research database read-only, handles logins (participant / administrator) and serves each participant only their own rows; the browser keeps a copy of the logged-in participant's data in **SQLite WASM on OPFS**. The plan is `docs/piano-multiutente.md`, the state of the work `docs/stato-lavori.md`. The old Bluetooth app (Gadgetbridge protocol port, demo band, FIT import) lives only in the branch `legacy-bluetooth`.

Language conventions: UI strings, README and log messages for the user are in **Italian**; code comments and identifiers are in English. Days and hours are always those of the study's time zone, Europe/Rome; the databases are in UTC.

## Workspaces

npm workspaces (`package.json` at the root, one `node_modules`):

- **`packages/core`** (`@bridge/core`): code with no browser or server dependency, used unchanged by the browser, the server and the tests — calendar of the study's zone (`time-zone`), `metrics`, `format`, `colors`, `goals`, `day-data`, `range-data`, `db/sql` + `db/queries`, `comparison/`, the datasets (`datasets.ts`) and schemas (`server/schema.ts` Garmin, `gima/schema.ts` Gima), the adapter from server tables to the app's tables (`adapters.ts` → `server/views.ts`), the browser copy and its sync (`sync/`). Consumed as TypeScript source (`"exports": { "./*": "./src/*.ts" }`), imported as `@bridge/core/<path>`. Its tsconfig has no DOM and no Node types: the compiler rejects browser or Node APIs there. Core never imports from `apps/*`.
- **`apps/web`** (`@bridge/web`): the React app, built as VitaBridge or HeartBridge (`--mode heartbridge` → `import.meta.env.VITE_APP`). `src/brand.ts`: name, device noun, the sections a device does not measure (`missing`: "hidden" or "unavailable" = «Non disponibile con questo dispositivo»; stress, energy, intensity, resting_hr, rem — the REM stage everywhere, `lib/sleep-stages.ts` —, restless), ECG / blood pressure / temperature / battery / active minutes; `brands/<app>/` icon and manifest, served and emitted by the `bridge-brand` plugin of `vite.config.ts`, which also sets `data-brand` on `<html>` (palette in `index.css`: HeartBridge coral, crimson errors, amber calories). Path alias `@/` → `apps/web/src/`.
- **`packages/server`** (`@bridge/server`, Node ≥ 24): Hono API, one process per app (`APP=vitabridge|heartbridge`), configuration only from environment variables (`src/config.ts`, `.env.example`; in development `.env` at the root). See "Server" below.
- **`packages/synth`** (`@bridge/synth`, development and tests only): FIT decoder/encoder and profile, the demo generator and cohort, `server/fit-to-server.ts` (Gadgetbridge's FitImporter), reading Gadgetbridge exports (`zip.ts`, `gb-export.ts`, `export-fixture.ts`), and the synthetic research databases (`garmin-db.ts` = demo generator + fit-to-server, `gima-db.ts` rows generated directly; some sections deliberately empty, the real invalid values included).

## Commands

```bash
npm install
npm run dev                      # API server (:8787, tsx watch) + Vite (:5173, proxies /api); extra args go to Vite: npm run dev -- --port 5174
npm run dev:heartbridge          # the same for HeartBridge: server :8788 on data/synthetic-gima.db (HEARTBRIDGE_DATA_FILE), Vite :5174 --mode heartbridge
npm run dev:web / dev:server     # one of the two
npm run gen:synthetic            # data/synthetic-garmin.db + data/synthetic-gima.db (made-up participants, real schemas); -- --out <dir> --cohort <n>
npm run admin:create -- <nome>   # new administrator (temporary password printed once, change forced, audit_log); never from the web
npm run admin:reset-password -- <nome>   # new temporary password for any account (administrator recovery); after the build: node packages/server/dist/admin.js
npm run admin:accept-source              # the accounts database accepts the data source now configured (the same data moved elsewhere); audit_log
npm run measure:compare -- <database>     # time and memory of one comparison cache build (read-only)
npm run build                    # apps/web for both apps (vite build -> apps/web/dist/, vite build --mode heartbridge -> apps/web/dist-heartbridge/) + packages/server (esbuild -> dist/server.js, dist/comparison-worker.js, dist/admin.js)
npm run preview                  # serves apps/web/dist (proxies /api like dev)
npm run typecheck                # tsc -b (all workspaces)
npm test                         # vitest run: projects core, core (TZ New York), synth, server (node, TZ=Europe/Rome), web (apps/web/tests: pure modules); vitest.global-setup.ts fails the run if any file in data/ changes or appears
npx vitest run --project server             # one workspace
npx vitest run packages/server/tests/sync.test.ts   # single test file
GB_EXPORT=data/gadgetbridge_*.zip npx vitest run packages/synth/tests/server-format.test.ts   # conversion against a real Gadgetbridge export (skipped without it; never commit an export)
npm run gen:fit-profile          # regenerate packages/synth/src/fit/profile.ts (needs ../Gadgetbridge checkout + python3)
```

There is no linter configured. CI (`.github/workflows/pages.yml`, Node 24) runs `npm test` then `npm run build` on every push to `main`, so both must pass (the GitHub Pages deploy goes away in Fase 6). `apps/web/vite.config.ts` uses `base: "./"`; keep asset paths relative (the app calls `api/...` relative to the page).

`packages/synth/src/fit/profile.ts` is generated — edit `scripts/gen-fit-profile.py` (the `WANTED` message set) instead.

`data/` (real research databases, the export) is never in git and is opened only read-only.

## Architecture

Data flow: **research server database (read-only copy) → `packages/server` (only the session's participant's rows, /api/data/*) → `core/sync` into the browser's copy (the server's own tables, SQLite on OPFS) → `core/adapters` (server tables → app tables, persistent in the copy) → `db/queries`, `day-data`, `range-data` → pages/charts.**

- **Study calendar** — `core/time-zone.ts`: `startOfDay`, `addDays`, `weekStart`, `monthStart`, `localParts`, `zonedTime`, `dayKey` in Europe/Rome via `Intl` (offset cached per hour); every date and hour of the app and of `format.ts` comes from here, never from Date's local getters. `tests/time-zone.test.ts` also runs with TZ=America/New_York.
- **Gima adapter** — `core/gima/views.ts` (`GIMA_VIEWS`, chosen by `adapters.ts VIEWS_OF`): the same app tables from the Gima tables (ms → s): each 30-minute step block spread over six 5-minute rows (exact integer parts), `DISTANCE_CM` holds METERS (×100), heart rate rows for the valid day, sleep stages (start + DURATION_SEC, 241 deep, 242 light, others unknown = stage 5, ignored by `sleepSessions`) as end boundaries with the pauses (< 3 h) awake and the night = the island of stages; `blood_pressure_sample`, `body_temperature_sample`, `hrv_value_sample.cvrr`, `ecg_recording` (metadata; samples read from `ECG_MEASUREMENTS` with `queries.ecgBlob` + `gima/ecg.decodeEcg`); invalid values filtered only here (`GIMA_VALID`); empty views for what Gima does not measure (`server/views.APP_COLUMNS`, Garmin has empty views for HeartBridge's tables). `core/gima/ecg.ts`: the ECG constants in one place (83.33 Hz = 250/3, unit «unità del dispositivo», ±500, both to be confirmed: the viewer warns) and the device's assessment with prudent words. `createViews`/`updateTables` take any list of views.
- **Adapter** — `core/server/views.ts` shows Gadgetbridge's Garmin tables as the app's tables: per-minute deltas of the cumulative day counters with LAG per user/device/local day (value at t covers the minute before), -1 → NULL, not-worn rows out, sleep stages as end boundaries, nights from event 74, ms → s; the day split uses the TEMP table `tz_offset` of the study's zone. `createLocalViews` (TEMP views/tables, for research databases: the server never writes to them) and `updateLocalTables` (persistent tables in the browser's copy, rebuilt only from a day on — see below). Every view's `select(from)` computes whole days from `from`, the same rows as the full select. Known limits of the Gadgetbridge format, kept on purpose: midnight totals can be overwritten by the next file; distance is partly lost (DISTANCE_CM often -1; per-file sums over activity types forget a type that does not come back in later files). Steps with no measured distance at or after them on the same day (`distance_missing`) get an estimate in `db/queries.ts`: steps × the person's average step length (`person_stride`, from their covered minutes, at least `MIN_STRIDE_MINUTES` 60 and `MIN_STRIDE_STEPS` 1000) or `DEFAULT_STRIDE_CM` 75; `distance_est_cm` / `distance_estimated_m` / `distanceEstimatedM` carry the estimated part and the UI labels it «stimata» (`format.estimatedLabel`). A loss hidden in the counter itself cannot be estimated.
- **Browser copy** — `core/sync/local-db.ts`: the dataset's health tables (from the server schema, without foreign keys), `device_info`, `meta` (owner = `CopyOwner`: app + username + participant id + code + the server's data source fingerprint; any change wipes the copy, `openOwnedCopy`; `source`; `dirty_from`). The sync refuses (`SourceChangedError`, nothing written) when `/api/data/counts` names another source than the copy's; the app then reloads `/api/auth/me`. `core/sync/sync.ts`: per table and device, a device absent from the copy is downloaded in full, otherwise its rows from (its latest time − 3 days) are replaced; then the row counts per table and device are compared with `/api/data/counts` and a mismatch downloads that device's table again; a device gone from the server is removed; a change of the server's data version restarts the sync once. Before touching the copy the sync marks `dirty_from` (seconds, or "all"); `app-context.tsx` then updates the app's tables from that day only (`updateAppTables`) and clears it: no rebuild at start.
- **Web app** — `App.tsx`: secure-context check (`window.isSecureContext`, clear message over http from a network address), login, forced password change, then `AdminApp` or the participant's app. `auth.tsx`: session from `/api/auth/me` (also the study rules: time zone, valid-day hours), logout hooks (the copy and its OPFS pool directory are erased first), last participant cached in `localStorage` (no token, no health data) to open the copy offline. `app-context.tsx` (`useApp`): the copy (`lib/db/client.ts` → `db.worker.ts`, one shared client per page: `sharedDbClient`, OPFS allows one worker on the files; OPFS file `/bridge-local.sqlite3` in the pool `vitabridge-pool`), sync at start / every hour / «Sincronizza» (`POST /api/data/refresh` first), goals from `/api/me/settings`, devices with the latest `BATTERY_LEVEL`, which sections the band ever recorded (`lib/empty-states.ts`), `performance.measure("bridge:open|sync|rebuild")`. Pages: Home (`dashboard.tsx`; HeartBridge: ECG card and «Pressione»), Grafici (`charts.tsx`; HeartBridge: Pressione, Temperatura, HRV/CVRR), ECG as a metric of Grafici (HeartBridge: `EcgDay` — the recording's values, the viewer, one button per time — and `EcgRange` — counts per assessment, one dot per recording, the list — in `pages/charts.tsx`; the pieces in `components/ecg-parts.tsx`, `components/charts/ecg.tsx`: the canvas, the zoom as paper speed in steps (12.5 · 25 · 50 · 100 mm/s, the grid keeps its size), the other charts' gestures (one finger or the mouse = reading «s · unità», two fingers / Ctrl + wheel / buttons = speed, mouse drag and horizontal wheel = move, double tap = 50 / back to 25, touch-action pan-y), the strip of the whole recording to move along it and the always-shown bar with «25 mm/s»; the dots chart uses the other charts' `Surface`, `Tooltip`, `Cursor`, `labelStep`; short assessment labels, «Valutazioni automatiche del dispositivo, non sono diagnosi mediche» once per box), Dispositivi (informative), Impostazioni (account, goals, theme, local copy). The OPFS pool is `<app>-pool`. Hash router `lib/router.ts`; hand-written SVG charts in `components/charts/` (a line breaks after a pause longer than 2.5 × the median interval of its series, never less than the chart's old fixed value, and isolated measures are dots: `core/line-gaps.ts`; SpO2 axes end at 100); shadcn (new-york) in `components/ui/`. `public/sw.js`: network-first cache of the app shell, never `/api/`. The phone's bottom menu has a fixed height (`--bottom-nav` in `index.css`): the content leaves exactly that room and `scroll-padding-bottom` / `-top` keep anything scrolled into view clear of the menu and of the sticky header.
- **Computations** — `core`: `metrics.ts`, `db/queries.ts`, `day-data.ts`, `range-data.ts` are aligned with Gadgetbridge's (sleep stage = end boundary of the period, Garmin stress bands, active + resting calories with the band's RMR prorated). A valid day = at least `getValidDayHours()` distinct hours with heart rate (default 12, `VALID_DAY_MIN_HOURS` on the server, sent to the app): one definition for the user and the others.
- **Comparison with other participants** — `core/comparison/`: `ComparisonSource`; per day (or Monday–Sunday week for intensity) the others' median, 25th–75th percentile, mean and n, null below the minimum (`MIN_USERS` 5, server `COMPARE_MIN_PARTICIPANTS`); the judgement between people (`MIN_VALID_DAYS` 7; today does not count in a period value until midnight, `daily-values.periodValue`) over the comparable days only: `CohortSource.comparableStanding` keeps the days already over (complete weeks for intensity) where the others' distribution exists, for the participant and the others alike, and returns how many (`comparable`) and `noOthers`; each app compares only `datasets.ts compareMetrics` (HeartBridge: steps, calories, sleep, SpO2, respiration, HRV — HRV from the day's values when there is no nightly summary; never blood pressure or temperature); `aggregate.summarySentence` says «Novembre, su 24 giorni confrontabili: … Fai più passi di circa 40 partecipanti su 100 …» with each metric's verb (`METRIC_WORDS`), `noOthersMessage` «Nessun altro partecipante ha dati sul sonno in questo periodo». `facts.ts`: each person's daily facts (`personFacts` = loadRange → `factsFromRange`) and `FactsComparisonSource` answering from them (`standingOf` = `comparableStanding` with the asking person's own values from the same facts); `server/server-source.ts` = the same over server databases. Server: `src/comparison/` — `build.ts` ATTACHes the data copy read-only to an in-memory database, builds the app's tables as TEMP tables and the facts; `worker.ts` runs it in a worker thread; `service.ts` (`ComparisonService`) keeps the cache per data version, rebuilds in the background and answers from the previous cache until the new one is ready; endpoints `/api/compare/daily|weekly|standing` (participants only, the asking participant left out from the session, only aggregates). Web: `lib/comparison/http-source.ts`; «Confronta» in `pages/charts.tsx` is page state (overlay, panel under the chart with «Partecipante tipico (mediana)», «Metà dei partecipanti», «Media (n = …)», partial bars left out).

## Server

- **Research data, read-only:** `src/data-source.ts` (`DataSource`): mode `file` (a local copy, development) or `backup` (periodic downloads of the existing server's `GET /admin/backup` with HTTP Basic, checked with `quick_check`, `user_version = 1` and core's schema, then an atomic rename; the last valid copy stays if a download fails; one download at a time, `refresh({ ifOlderThanMs })` for «Sincronizza»). Copies are always opened with `file:…?mode=ro&immutable=1` + `readOnly` + `PRAGMA query_only` (`src/sqlite.ts`): no -wal/-shm files are created next to them. Never open `data/*.db` any other way.
- **Datasets:** `packages/core/src/datasets.ts` is the single list of each app's schema, the tables a copy must have, the health tables a participant may download and the device columns that may be shown (never `identifier`/`hardware_id`).
- **Isolation:** `src/participant-data.ts` is the only module reading health tables (`readRows` with optional device filter, `countsOf`, `devicesOf`); the participant id always comes from the session, table and column names from the dataset and the copy's schema.
- **Account ↔ participant** (`src/auth/link.ts`): a participant account keeps the participant's id AND code (`participant.name`, unique). Before any data (`linked` middleware in `app.ts`: `/api/data/*`, `/api/compare/*`), at login and in the administrator's list, `enforceLink` checks that id and code still go together in the data copy in use: otherwise 403 without data, `link_state` «da verificare» (`review`) and `account_flagged` in the audit log (once); they go back to `ok` by themselves when id and code match again (`account_restored`). If the code has another id, only an administrator relinks it with one click (`POST /api/admin/accounts/:id/relink` with id and code, `account_relinked`); if the code is gone, the account stays blocked. Accounts made before the codes were kept are «da ricreare» (`recreate`), never valid again. Accounts are created with id AND code (refused if they no longer match). The comparison finds the requester by code, never by id. The participant's app shows «Account da verificare / da ricreare» and erases the device's copy. Participants never get `participant`, `collection_request`, `upload_batch`, keys or tokens; administrators never get health data. `tests/isolation.test.ts` proves it on both apps.
- **Auth database** (`AUTH_DB`, separate from the data, written only by us; append-only `MIGRATIONS` in `src/auth/store.ts`): `account`, `session` (SHA-256 of the cookie token, CSRF token, inactivity expiry per role: participants 30 days, administrators 8 hours, configurable), `audit_log` (account actions), `account_settings` (the participant's goals, `core/goals.ts`), `auth_meta` (the data source the database is bound to: fingerprint of app + mode + absolute path or backup URL, `config.dataSourceId`; at startup `bindSource` refuses another source with a clear message; `npm run admin:accept-source` binds it to the new one). Without `AUTH_DB` the file is named after the data in mode file (`auth/vitabridge-synthetic-garmin-auth.db`), `auth/<app>-auth.db` in mode backup. Migration 3 rebuilds `account`/`audit_log` with foreign keys off (checked before they are turned on). Passwords with scrypt; temporary passwords are returned only once. Administrator accounts are created and recovered only with `src/admin-cli.ts` on the server (audit author `cli:<system user>`); the first one also from `ADMIN_USERNAME`/`ADMIN_PASSWORD`.
- **Request rules** (`src/app.ts`): non-GET requests need `Origin` = `PUBLIC_ORIGIN` and, once logged in, `X-CSRF-Token`; login limited per username and per IP (`TRUST_PROXY` → last `X-Forwarded-For` entry); error answers are short Italian messages. The only logger is `src/log.ts`, which hides secret-named fields and the configured secrets; `tests/secrets.test.ts` checks that no password, token, cookie or backup credential reaches the log or an error answer.

## Tests

vitest in node; SQLite is the real `@sqlite.org/sqlite-wasm` in memory (the browser's engine) or `node:sqlite` on the server side.
- `packages/core/tests`: `time-zone` (two zones), `metrics`, `comparison`, `gima` (the Gima adapter on hand-written rows: blocks, split night, invalid values, ECG, partial = full update), `sleep` (a real night through fit-to-server → views), `views` (counters → per-minute values, comparison on the server's participants), `server-format-synthetic` (hand-written FIT files and the expected Gadgetbridge rows, band on Tokyo time), `export-verification` (the new adapter on the rows of a real export against the legacy app's values from the same export's FIT files, `fixtures/export-expected.json`: numbers only). The rows are personal health data and never go into git: `data/export-device4.json` (made with `packages/synth/src/export-fixture.ts`) or `$EXPORT_ROWS`; the test is skipped without them.
- `packages/server/tests`: `isolation`, `auth`, `secrets`, `settings`, `config`, `admin-cli`, `data-source`, `gima-real` (the Gima adapter on `data/GimaDB.db` against the database's own night totals, valid values, 83.33 Hz; skipped without it, nothing from it in git), `link` (accounts made on one database refused on another, accepted source → no data until relinked, same id with another code → blocked, creation only with matching id and code, old accounts «da ricreare», accounts file named after the data), `compare` (same numbers as core's comparison, requester left out, minimum, only aggregates, previous cache during a rebuild, copy never written), `sync` (core's sync against the real server in process: exact copy, per-device windows, count mismatch → full download of that device's table, partial rebuild = full rebuild, a copy is wiped when account, participant or data source change, the sync writes nothing from another source).
- `packages/synth/tests`: the synthetic databases, the data/ guard (`src/data-guard.ts`); `server-format` the FIT → Gadgetbridge rows conversion against a real export (`GB_EXPORT`).
